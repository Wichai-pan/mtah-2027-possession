## 1. 评价指标：spellF1 是怎么算的

1. 把真值和预测都切成"控球段"，也就是连续的 H 或连续的 A。**D 不算控球段**，它是两段之间的停顿。
2. 预测的控球段和真值的控球段按时间重叠比例（IoU）**一对一配对**，而且必须是同一队。
3. 在 IoU 阈值 0.3、0.4、0.5、0.6、0.7 下各算一次 F1，再取平均。

这个指标有几个直接的后果：

| 现象 | 对 spellF1 的影响 |
|---|---|
| 一段控球开始晚了 1 秒 | 从 1.0 掉到 0.65；晚 1 帧不扣分 |
| 一段控球被切成两半 | 两半都可能配对失败，同时还多出一段误报 |
| 预测的段数过多（每帧单独判断导致来回跳） | 灾难性的。官方原始基线 macroF1 有 0.65，spellF1 却只有 0.05 |
| 漏掉一些很短的控球 | 代价相对较小，比瞎猜要好 |
| 计分帧上写 **X** | spellF1 会自动用"上一个标签"补上：在一段控球中间写 X 不扣分；在换队的时刻写 X 就很亏 |

还有两个需要知道的数字：

- 全场分数相差不到 **0.04**，基本可以看作噪声。
- 公开 5 分钟里只有 17 段控球，**多对或多错一段，分数就会差大约 6 个点**。所以公开 5 分钟**不能用来比较两个版本谁更好**。官方的例子就是：在 5 分钟上表现最好的平滑窗口，放到全场反而更差。

**我们的优先级**：段数要合理、不要切碎 > 死球的起止时刻 > 看不到球时判断是哪队在控球 > 逐帧准确率。

## 2. 我们有哪些数据

### 比赛官方提供的输入（不能外传）

| 数据 | 内容 | 目前是否使用 |
|---|---|---|
| 战术机位跟踪数据（ATD） | 每帧 46 个跟踪编号的 x、y、速度，以及球的 x、y。**只知道属于哪一队，不知道是谁**。没有球的高度。计分帧中有 41% 看不到球 | ✅ 主要输入 |
| 战术机位视频 | 广角镜头，帧号和提交文件的行号一一对应 | 只用来可视化 |
| 单应矩阵 | 球场坐标和画面像素的换算关系 | 只用来可视化 |
| Smart Tagging | 638 段自动标注的**战术阶段**，以及**定位球**（角球、任意球、界外球、球门球、开球），大多带球队。**不是真值** | 已评估，还没接入模型 |
| 转播机位的视频和跟踪数据 | 和战术机位**不同步** | 不用 |
| 公开 5 分钟真值 | 第 11185–18684 帧 | **只用来检查流程** |

### 外部训练数据

**DFL / IDSSE 数据集**：Bassek, Rein, Weber & Memmert (2025), *Scientific Data* 12:195, [doi:10.1038/s41597-025-04505-y](https://doi.org/10.1038/s41597-025-04505-y)；数据下载 [figshare 28196177](https://doi.org/10.6084/m9.figshare.28196177)，许可证 CC-BY 4.0。

- 包括 7 场德甲比赛：TRACAB 采集的**修正后**跟踪数据（含球的高度 z），以及官方事件数据。
- **每一帧都有控球方和死球标记**（`BallPossession`、`BallStatus`）。
- 我们选它的原因：主办方说比赛真值也是"从修正后的跟踪数据机械推导出来的"，和 DFL 这类标签的来源性质相同。
- SoccerNet 等其他数据集没有用。原因是它们没有逐帧的控球标签，只适合用来改进球的检测，性价比低。

## 3. 方法：现在的流程（v2）

```
DFL 7 场（干净数据）──► 降质（模拟比赛数据的噪声）──► 训练集
      │                                                 │
      └─► 按官方定义改写标签（relabel）────────────────►┘ 标签

比赛 ATD ──► 无身份特征 ──► 死球模型 P(D)          ┐
                       └─► 控球模型 P(H | 活球)    ┘─► Viterbi 解码 ─► H/A/D 序列 ─► CSV（非计分帧写 X）
```

1. **降质** `degrade.py`：DFL 的数据太干净，我们照着比赛数据的统计特征把它"弄脏"：
   - 球缺失约 41%，而且是成段缺失；
   - 跟踪编号会断开，换成新的编号（单段长度中位数约 35 秒）；
   - 每帧随机丢掉约 5% 的球员。

   这些参数都是从比赛数据上量出来的。**验证**：官方基线在降质后的 DFL 上得 0.231，在比赛全场上是 0.2433，两者接近，说明降质后的数据比较像真的比赛数据。
2. **改写标签** `relabel.py`：DFL 的控球方在每次触球时都会翻转。官方定义要求"控制住球"才算换队，所以我们把短于 2 秒、而且只有不到 3 个人碰过球的控球段，并入前一段控球。具体规则写在 [docs/possession_rules.md](possession_rules.md)。
3. **死球模型** `deadball.py`：梯度提升分类器，**只用球员特征**（全队速度、阵型分散程度等多个时间尺度的统计量），不用球的特征。原因是 DFL 死球时球的坐标被冻结，用了球的特征模型会作弊。
4. **控球模型** `possession_model.py`：梯度提升分类器，用每队的特征：最近球员离球的距离、之前和之后一段时间内的最近距离、距离上次 / 下次靠近球过了多久、球附近每队有几个人、朝进攻方向推进了多少等。训练时把主客队互换一遍，作为数据增强。
5. **解码** `decode.py`：三个状态的 Viterbi，包括换队代价、进出死球的代价，以及每种状态的最短持续时间（H/A 至少 2 秒，D 至少 5 秒）。参数是在 DFL 的 4 场上调的，在另外 3 场上验证。

**只有两个模型需要训练，训练一次大约 40 秒**，用普通 CPU 就够。提交文件可以完全复现，两次运行生成的文件逐字节相同。

## 4. 关于"真值"：有三层，可信度依次不同

| 层级 | 是什么 | 用途 | 可信度 |
|---|---|---|---|
| 主办方私有的全场真值 | 本场比赛，由 Metrica 修正后的跟踪数据推导而来 | 最终排名 | 我们看不到 |
| 公开的 5 分钟 | 上面那份真值的前 5 分钟 | **只能用来检查**：帧有没有对齐、标签含义有没有理解对 | 准，但样本太少 |
| **DFL + 我们的改写** | DFL 修正后的标签，按我们对官方定义的理解改写 | 训练、调参、选版本 | **定义可能有偏差** |

DFL 这一层是我们自己构造的"真值"，有两个风险：

1. **"控制住球"的判断标准不一样**：Metrica 的规则我们看不到，"2 秒、3 个人"是我们根据官方文字描述定的。
   - 支持的证据：改写后，控球段平均长 11.0 秒、中位数 6.8 秒，公开 5 分钟里分别是 14.2 秒和 7.6 秒，比较接近；改写前只有 7.3 秒和 3.8 秒。
   - 应对办法：让结果对这个阈值不敏感，比如分别用 1.5、2、3 秒改写标签，看名次会不会变。
2. **"死球"的标准不一样**：DFL 的死球是数据员标的，Metrica 的死球来自它自己的跟踪数据，两边的起止时刻可能差几秒。我们在公开窗口里看到 v2 判断恢复比赛的时刻有偏晚的例子，但只有一个样本。

**验收原则**：一个改动只有在 DFL 上留出的比赛里提升，并且提升超过噪声范围时才合并。公开 5 分钟只用来确认没有把东西接错。

## 5. 已知问题和已有发现

- ❗ **下半场开球前有 2,934 帧**（第 110,808–113,741 帧）也计分，而且全部是 D，但 v2 把其中 1,013 帧判成了 H。修正方法：用 Smart Tagging 的开球标签加上跟踪数据，检测出开球时刻，在这之前一律判 D。**还没改**，改动很小，但必须做。
- **Smart Tagging 的评估结果**（全场，不用真值；脚本 `scripts/eval_smart_tagging.py`）：
  - 定位球标签大多数对应真实的死球：标签开始后 2 秒内球员速度很慢的比例是 81%，随机时刻只有 48%；
  - **漏标很多**，只覆盖了大约四成的停顿，任意球只标了 5 个；
  - 标签开始和实际恢复比赛之间的时间差**不固定**，公开窗口里的两个例子分别是 3 秒和 12 秒；
  - 进攻和防守阶段是**成对的重复信息**，覆盖了 82% 的活球帧，和 v2 判断的控球方一致率是 76%。
- 全场 v2 判出 48% 的死球。正常比赛的有效比赛时间约 55–60 分钟，计分时段是 106 分钟，所以 40–48% 的死球比例是合理的，但有可能偏高。
- 只靠球的数据检测恢复比赛很困难：定位球前后只有约 30% 的时间能看到球。

## 6. 规则要点（违反了会被取消资格）

- **不能对本场比赛做任何人工标注**，包括人工修正跟踪数据、把看视频时记下的帧号写进规则或参数。**看视频本身是允许的**，只能用来理解数据。
- **公开 5 分钟不能用来训练、调参或挑选版本**。
- 不能使用本场比赛的任何人工数据，比如 Opta、StatsBomb 的事件数据。其他比赛的数据随便用，但要在文档里写明来源。
- **不能把比赛的视频、数据或其中任何片段发给云端 LLM**，包括 ChatGPT、Claude 网页版这类服务。用 AI 写代码可以，但别把数据内容贴进对话。
- 代码仓库必须**公开**，并且能**逐字节复现**提交文件；仓库里**不能有比赛数据**，`.gitignore` 已经配置好了。
- 提交时，CSV 和 PDF 都用队名命名，通过 Google 表单提交，每队只算最后一次提交。

## 8. 如何上手

```bash
git clone <我们的仓库>  && cd <仓库>
uv sync                                   # 安装依赖（Python 3.11，版本已锁定）
uv run pytest -q                          # 6 个测试应该全部通过
```

需要准备的数据（都不进仓库）：

- 比赛数据：每个人用自己报名后拿到的链接下载，按官方结构放到 `../repo/data/`，其中 `../repo` 是官方仓库的 clone。
- DFL 数据：从 figshare 下载，放到 `../external_data/dfl/raw`，再运行 `uv run python scripts/prepare_dfl.py`，大约需要 1 分钟。

常用命令：

```bash
uv run python scripts/eval_dfl.py --versions degraded --targets official --methods pipeline_v2   # DFL 上的成绩
uv run python scripts/make_submission.py --data-dir ../repo/data --out results/submission.csv   # 生成提交文件并校验
uv run python scripts/eval_smart_tagging.py                                                     # Smart Tagging 评估（只输出统计数字）
```

代码结构和每一阶段的实验记录见 [README.md](../README.md)。
